Separating computation from generation

Séparer le calcul de la génération

How I prevented unsupported numerical values from reaching a generated production report, and the three problems this does not address.

Comment j'ai empêché toute valeur numérique non fondée d'atteindre un rapport de production généré, et les trois problèmes que cela ne règle pas.

At a hockey equipment factory I built an AI reporting agent for the quality team. Once a week they review production defects, and the agent writes the analysis they read: what changed, where defects concentrated, and which trends persisted across sixty weeks.

The dataset was 7,780 defect records. The model was Llama 3.3 70B, self-hosted on vLLM because production data could not leave the site. Neither of those is the interesting part.

The interesting part is that the agent has never reported an incorrect figure in a meeting, and that this is the only reason it remained in use.

Why a single incorrect figure ends adoption

Trust in a reporting tool is not lost gradually. If an engineer reads that defects rose 12%, opens the source spreadsheet and finds 8%, the tool is finished. Not degraded, finished. They stop reading it, and they stop believing the figures it reported correctly, because there is no way to tell which is which without checking all of them by hand.

The requirement was therefore not high average accuracy. It was zero incorrect figures. A system that is correct 95% of the time produces a wrong value in roughly every fifth meeting, which over a quarter is several occasions on which it loses the room. For this use case, 95% is not a good score. It is a slower path to the same outcome.

That reframing determined the design. The goal was not to make the model more accurate. It was to make one class of error structurally impossible.

The pattern

The model is never permitted to produce a number.

Python computes every quantity that will appear in the report. The model receives those quantities pre-computed and pre-formatted, and its only responsibility is to arrange them into readable French prose. It writes from a fact sheet rather than performing analysis.

The values arrive as strings, already formatted for French conventions: comma decimal separator, non-breaking space before the percent sign. This matters more than it appears. If the model can copy a token verbatim, copying becomes the path of least resistance. Passing it 0.083 and requesting a percentage is an invitation to perform arithmetic.

Validation is the substantive work

Constraining the prompt is not sufficient. Models drift over long outputs, particularly when the natural continuation of a sentence is a number.

After generation, every numerical value in the output is checked against the set Python computed. Anything outside that set did not originate in the data, by definition.

Extracting numbers from French prose is less straightforward than it appears. 88,1 % uses a comma as the decimal separator. 7 780 uses a space as the thousands separator, sometimes a narrow non-breaking space. Splitting on whitespace does not work.

The permitted set is every computed value plus an explicit allowlist, and that allowlist is where the false positives accumulate. The first version rejected the phrase "taux de 2,7 par 100 unités". Both numbers are correct, but 100 is not a data value at all: it belongs to the expression "per 100 units". Week numbers, station identifiers and the year raised the same issue. Maintaining that list is the real cost of the approach.

The failure mode I did not anticipate

The model does not fabricate values at random. It fabricates derived quantities.

Given 412 defects this week and 380 last week, it will write "an increase of 32, approximately 8%". Both values are correct. Neither is in the fact dictionary. Both are rejected.

This imposed a discipline I would not have arrived at otherwise: any quantity you want mentioned has to be computed first. Differences, percentages, ratios, rates per hundred, the length of a trend. The fact dictionary roughly tripled in size once I understood this, and the rejection rate fell sharply.

There is a useful property here. The set of values the model is permitted to state is exactly the set I have decided is meaningful, so the constraint also functions as editorial control.

Falling back rather than retrying indefinitely

When validation fails, the obvious response is to retry with a stricter prompt. The system allows two attempts. After that it stops generating and renders a deterministic template. The template is rigid, repetitive, and visibly machine-written. It is also incapable of reporting an unsupported value.

That was the hardest decision to make and the easiest to defend afterwards. A report that occasionally reads awkwardly is a minor inconvenience. A report that occasionally misstates a figure is not usable.

What this does not address

The limits are worth stating precisely, because the approach is narrower than a phrase like "prevents hallucination" implies.

It validates values, not claims. If the model states that defects are declining while every figure it quotes is correct and rising, validation passes. The numbers are right and the sentence is wrong. Directional and causal language is unchecked in the current implementation. This is the largest gap.

The tolerance is a compromise. A small absolute tolerance prevents legitimate rounding from being rejected. That same tolerance is a window through which small errors pass.

It cannot detect omission. Three accurate sentences that silently skip the most significant finding in the data will validate perfectly.

There is no measure of quality. I can state that the system has never emitted an incorrect figure. I cannot state whether the summaries are useful, whether they surface the right findings, or whether last month's prompt change improved them. Correctness without evaluation is half an engineering practice.

What I would build next

Validate direction as well as magnitude: compute the sign of every change and reject prose whose directional vocabulary contradicts it. This is roughly a day of work and it closes the largest gap.

Build a reference set. Fifty fact dictionaries with human-written summaries and a score, so that prompt changes stop being guesses.

Track rejections as a first-class metric rather than a log warning. The rejection rate over time is a real signal about model drift and about the coverage of the fact dictionary.

If you are placing a language model in front of people who will check its arithmetic, the useful question is not how to make it more accurate. It is which class of error you can eliminate structurally, and what you are prepared to ship instead when you cannot.

Dans une usine d'équipement de hockey, j'ai construit un agent de reporting pour l'équipe qualité. Chaque semaine, elle passe en revue les défauts de production, et l'agent rédige l'analyse qu'elle lit : ce qui a évolué, où les défauts se concentrent, quelles tendances persistent sur soixante semaines.

Le jeu de données comptait 7 780 enregistrements de défauts. Le modèle était un Llama 3.3 70B, auto-hébergé sur vLLM parce que les données de production ne pouvaient pas sortir du site. Ce n'est pas là que réside l'intérêt.

L'intérêt tient à ce que l'agent n'a jamais rapporté un chiffre erroné en réunion, et que c'est la seule raison pour laquelle il est resté en service.

Pourquoi un seul chiffre erroné met fin à l'adoption

La confiance envers un outil de reporting ne s'érode pas progressivement. Si un ingénieur lit que les défauts ont augmenté de 12 %, ouvre le tableur source et y trouve 8 %, l'outil est fini. Non pas affaibli : fini. On cesse de le lire, et l'on cesse de croire les chiffres qu'il avait rapportés correctement, faute de pouvoir distinguer les uns des autres sans tout revérifier à la main.

L'exigence n'était donc pas une exactitude moyenne élevée, mais zéro chiffre erroné. Un système juste 95 % du temps produit une valeur fausse environ une réunion sur cinq, soit plusieurs occasions par trimestre de perdre la salle. Pour cet usage, 95 % n'est pas un bon score : c'est un chemin plus lent vers le même résultat.

Ce cadrage a déterminé la conception. Il ne s'agissait pas de rendre le modèle plus exact, mais de rendre une classe d'erreurs structurellement impossible.

Le principe

Le modèle n'a jamais le droit de produire un nombre.

Python calcule chaque quantité qui figurera dans le rapport. Le modèle les reçoit déjà calculées et déjà mises en forme, et sa seule responsabilité est de les organiser en français lisible. Il rédige à partir d'une fiche de données, il ne fait pas d'analyse.

Les valeurs arrivent sous forme de chaînes, déjà conformes aux conventions françaises : virgule décimale, espace insécable avant le signe pourcent. Ce détail compte plus qu'il n'y paraît. Si le modèle peut recopier un élément tel quel, la recopie devient la voie de moindre effort. Lui transmettre 0.083 en demandant un pourcentage revient à l'inviter à calculer.

La validation constitue le vrai travail

Contraindre le prompt ne suffit pas. Les modèles dérivent sur les textes longs, en particulier lorsque la suite naturelle d'une phrase est un nombre.

Après génération, chaque valeur numérique du texte est comparée à l'ensemble calculé par Python. Tout ce qui n'y figure pas ne provient pas des données, par définition.

Extraire des nombres d'un texte français est moins simple qu'il n'y paraît. 88,1 % emploie la virgule comme séparateur décimal. 7 780 emploie l'espace comme séparateur de milliers, parfois une espace fine insécable. Découper sur les espaces ne fonctionne pas.

L'ensemble autorisé réunit toutes les valeurs calculées et une liste d'exceptions explicite, et c'est dans cette liste que s'accumulent les faux positifs. La première version rejetait la formule « taux de 2,7 par 100 unités ». Les deux nombres sont justes, mais 100 n'est pas une donnée : il appartient à l'expression « par 100 unités ». Les numéros de semaine, les identifiants de poste et l'année ont posé le même problème. Tenir cette liste à jour est le coût réel de la méthode.

Le mode de défaillance que je n'avais pas anticipé

Le modèle n'invente pas des valeurs au hasard. Il invente les quantités dérivées.

Avec 412 défauts cette semaine et 380 la semaine précédente, il écrira « une hausse de 32, soit environ 8 % ». Les deux valeurs sont justes. Aucune ne figure dans le dictionnaire de faits. Les deux sont rejetées.

Cela impose une discipline à laquelle je ne serais pas parvenue autrement : toute quantité que l'on souhaite voir mentionnée doit d'abord être calculée. Écarts, pourcentages, rapports, taux pour cent, durée d'une tendance. Le dictionnaire a environ triplé de taille une fois ce point compris, et le taux de rejet a fortement chuté.

Basculer plutôt que réessayer indéfiniment

Lorsque la validation échoue, le réflexe est de réessayer avec un prompt plus strict. Le système autorise deux tentatives. Ensuite, il cesse de générer et produit un gabarit déterministe, rigide, répétitif et visiblement écrit par une machine. Il est aussi incapable de rapporter une valeur non fondée.

Ce que cela ne règle pas

La validation porte sur les valeurs, pas sur les affirmations. Si le modèle écrit que les défauts diminuent alors que tous les chiffres cités sont justes et en hausse, la validation passe. Les nombres sont exacts et la phrase est fausse. Le vocabulaire de direction et de causalité n'est pas contrôlé dans l'implémentation actuelle. C'est la plus grande lacune.

La tolérance est un compromis. Une petite tolérance absolue évite de rejeter un arrondi légitime. Cette même tolérance laisse passer les petites erreurs.

L'omission échappe au contrôle. Trois phrases exactes qui passent sous silence le constat le plus important seront validées sans réserve.

Il n'existe aucune mesure de qualité. Je peux affirmer qu'aucun chiffre erroné n'a été publié. Je ne peux pas dire si les synthèses sont utiles, si elles font ressortir les bons constats, ni si la dernière modification du prompt les a améliorées. La justesse sans évaluation ne constitue que la moitié d'une pratique d'ingénierie.

Si vous placez un modèle de langage devant des personnes qui vérifieront son arithmétique, la question utile n'est pas de le rendre plus exact. C'est de déterminer quelle classe d'erreurs vous pouvez éliminer structurellement, et ce que vous acceptez de livrer à la place lorsque vous ne le pouvez pas.
