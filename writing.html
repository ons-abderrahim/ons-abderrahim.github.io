Python computes, the LLM writes

Python calcule, le LLM rédige

How I stopped a reporting agent from ever showing a wrong number, and the three things this still doesn't solve.

Comment j'ai empêché un agent de reporting d'afficher un seul chiffre erroné, et les trois choses que ça ne règle toujours pas.

I spent this year building an AI agent for a hockey equipment factory. Once a week the quality team reviews production defects, and my agent writes the analysis they read: what moved, where defects concentrated, which trends held over sixty weeks.

The dataset was 7,780 defect records. The model was Llama 3.3 70B, self-hosted on vLLM because production data could not leave the building. None of that is the interesting part.

The interesting part is that the agent has never shown a wrong number in a meeting, and that this was the only reason anyone kept using it.

Why one wrong number kills the whole thing

Adoption of a reporting tool is not a gradient. It is a step function with a cliff.

If an engineer reads that defects rose 12% and then checks the spreadsheet and finds 8%, the tool is finished. Not degraded. Finished. They stop reading it, and worse, they stop trusting the three numbers it got right. Nobody wants to fact-check a robot every Tuesday morning.

So the requirement was not high accuracy. It was zero. A system that is right 95% of the time produces a wrong figure roughly every fifth meeting, which over a quarter is several credibility-destroying events. For this use case, 95% is not a good score. It is a guarantee of failure on a slower timeline.

That reframing drove the design. I was not trying to make the model more accurate. I was trying to make a category of error impossible.

The pattern

The model is never allowed to produce a number.

Python computes every quantity that will appear in the output. The LLM receives those quantities pre-computed and pre-formatted, and its entire job is to arrange them into readable French prose. It is a writer with a fact sheet, not an analyst.

The values arrive as strings, already formatted for French: comma decimals, non-breaking space before the percent sign. This matters more than it looks. If the model can copy a token verbatim, copying is the path of least resistance. Hand it 0.083 and ask for a percentage, and you have invited it to do arithmetic.

Verification is the actual work

Constraining the prompt is not enough. Models drift, especially over long outputs, and especially when a sentence has an obvious next word that happens to be a number.

So after generation, every number in the output is checked against the set Python computed. Anything not in that set did not come from the data, by definition.

Extracting numbers from French prose is fiddlier than it sounds. 88,1 % uses a comma decimal. 7 780 uses a space as a thousands separator, sometimes a narrow no-break space. You cannot naively split on whitespace.

The allowed set is every computed value plus a whitelist, and building that whitelist is where the false positives live. The first version rejected the sentence "taux de 2,7 par 100 unités". Both numbers are correct, but 100 is not a data value at all. It is part of the phrase "per 100 units". Same story with week numbers, station identifiers and the year. That maintenance cost is the honest price of the pattern.

The lesson I did not expect

The model does not hallucinate randomly. It hallucinates derived quantities.

Given 412 defects this week and 380 last week, it will happily write "an increase of 32, or roughly 8%". Both correct. Neither in my facts dictionary. Both rejected.

This forced a discipline I would not have arrived at otherwise: if you want a quantity mentioned, you must compute it. Deltas, percentages, ratios, rates per hundred, run lengths of a trend. My facts dictionary roughly tripled once I understood this, and rejection rates fell sharply.

There is a nice property here. The set of numbers the model is allowed to say is exactly the set I have decided are meaningful. The constraint doubles as editorial control.

Falling back rather than trying harder

When verification fails, the obvious move is to retry with a stricter prompt. I allow two attempts. After that, the system stops trying to be eloquent and renders a deterministic template. It is stiff, repetitive, and obviously machine-written. It is also incapable of being wrong.

This was the hardest decision to make and the easiest to defend afterwards. A system that occasionally reads awkwardly is a minor annoyance. A system that occasionally lies is not a system.

What this does not solve

I want to be precise about the limits, because the pattern is narrower than the phrase "anti-hallucination" suggests.

It verifies numbers, not claims. If the model writes that defects are falling while every figure it quotes is correct and rising, verification passes. The numbers are right and the sentence is wrong. Directional and causal language is completely unchecked in my current implementation. This is the biggest hole and I know it.

Tolerance is a compromise. I allow a small absolute tolerance so legitimate rounding is not rejected. That tolerance is also a window in which small errors pass.

It cannot catch omission. Three accurate sentences that silently ignore the most important finding in the data will verify perfectly.

I have no measure of quality. I can tell you the system has never emitted a wrong number. I cannot tell you whether the summaries are any good, whether they surface the right findings, or whether last month's prompt change made them better. Correctness without evaluation is half an engineering practice.

What I would build next

Verify direction as well as magnitude: compute the sign of every delta and reject prose whose directional vocabulary contradicts it. A day of work, and it closes the largest gap.

Build a golden set. Fifty fact dictionaries with human-written reference summaries, and an actual score, so prompt changes stop being guesses.

Log rejections as a first-class metric rather than a warning line. The rejection rate over time is a real signal about model drift and about my own fact coverage.

If you are putting a language model in front of people who will check its arithmetic, the useful question is not how to make it more accurate. It is which class of error you can make structurally impossible, and what you are willing to ship instead when you cannot.

J'ai passé cette année à construire un agent IA pour une usine d'équipement de hockey. Une fois par semaine, l'équipe qualité passe en revue les défauts de production, et mon agent rédige l'analyse qu'elle lit.

7 780 enregistrements de défauts. Llama 3.3 70B, auto-hébergé sur vLLM parce que les données de production ne pouvaient pas sortir du bâtiment. Rien de tout cela n'est la partie intéressante.

La partie intéressante, c'est que l'agent n'a jamais affiché un chiffre erroné en réunion, et que c'est la seule raison pour laquelle quelqu'un a continué à l'utiliser.

Pourquoi un seul chiffre faux tue tout

L'adoption d'un outil de reporting n'est pas un dégradé. C'est une fonction en escalier avec une falaise.

Si un ingénieur lit que les défauts ont augmenté de 12 %, vérifie le tableur et trouve 8 %, l'outil est fini. Pas dégradé. Fini. On cesse de le lire, et pire, on cesse de croire les trois chiffres qui étaient justes.

L'exigence n'était donc pas une haute précision. C'était zéro. Un système juste 95 % du temps produit un chiffre faux environ une réunion sur cinq, soit plusieurs événements destructeurs de crédibilité par trimestre. Pour cet usage, 95 % n'est pas un bon score : c'est une garantie d'échec à retardement.

Le patron

Le modèle n'a jamais le droit de produire un nombre.

Python calcule chaque quantité qui apparaîtra dans la sortie. Le LLM les reçoit déjà calculées et déjà formatées, et son unique rôle est de les organiser en prose française lisible. C'est un rédacteur avec une fiche de données, pas un analyste.

La vérification est le vrai travail

Contraindre le prompt ne suffit pas. Les modèles dérivent, surtout sur les sorties longues. Après génération, chaque nombre du texte est confronté à l'ensemble calculé par Python. Tout ce qui n'y figure pas ne vient pas des données, par définition.

L'ensemble autorisé comprend aussi une liste blanche, et c'est là que vivent les faux positifs. La première version rejetait « taux de 2,7 par 100 unités » : les deux nombres sont justes, mais 100 n'est pas une donnée, c'est une partie de l'expression.

La leçon inattendue

Le modèle n'hallucine pas au hasard. Il hallucine des quantités dérivées.

Avec 412 défauts cette semaine et 380 la semaine dernière, il écrira volontiers « une hausse de 32, soit environ 8 % ». Les deux sont corrects. Aucun n'est dans mon dictionnaire de faits. Les deux sont rejetés.

Cela impose une discipline : si vous voulez qu'une quantité soit mentionnée, vous devez la calculer. Mon dictionnaire a triplé de taille une fois que je l'ai compris.

Ce que ça ne règle pas

Ça vérifie les nombres, pas les affirmations. Si le modèle écrit que les défauts baissent alors que tous les chiffres cités sont justes et en hausse, la vérification passe. C'est le plus gros trou, et je le sais.

Ça ne détecte pas l'omission. Trois phrases exactes qui ignorent silencieusement la découverte la plus importante passeront parfaitement.

Je n'ai aucune mesure de qualité. Je peux affirmer qu'aucun chiffre erroné n'est jamais sorti. Je ne peux pas dire si les résumés sont bons. La justesse sans évaluation, c'est la moitié d'une pratique d'ingénierie.

Si vous mettez un modèle de langage devant des gens qui vérifieront son arithmétique, la bonne question n'est pas comment le rendre plus exact. C'est quelle classe d'erreur vous pouvez rendre structurellement impossible, et ce que vous acceptez de livrer à la place quand vous ne le pouvez pas.
